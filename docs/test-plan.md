# Test Plan

This document tracks manual bench validation for the current LED-only build.
Hardware-independent protocol and sequence behavior is covered by ztest under
`tests/`.

## Results

A test counts as passed only after it has been run against the application
firmware on the bench. Running the temporary I/O test sketch does not count: it
proves the wiring, not this firmware.

bench. Bench tests still marked `pre-auth firmware` must be rerun with a
provisioned shared key before range testing. Update this table in the same
commit that runs a test, so `docs/status.md` never claims more than this table
supports.

Phase 8 is not marked done in `docs/status.md` while TEST-003, TEST-011, and
TEST-012 are outstanding. Those three are the failure paths of authentication:
a lost ACK, a replayed packet, and a bad tag. Twister proves the filter and the
HMAC in isolation; none of them has run against the firmware with real NVS
state on the bench, which is the standard this table sets in its first line.

## Bench Notes - 2026-08-15

- TEST-001, authenticated firmware: after storage provisioning, TX booted with
  an empty sequence store and RX booted with an empty replay store. One TX
  button press produced authenticated `COMMAND(TRIGGER) seq=1`; RX logged the
  command with RSSI `-41` and SNR `7`, pulsed the actuator, sent authenticated
  ACK `seq=1`, and TX logged the matching ACK with RSSI `-42` and SNR `8`.
- TEST-001, authenticated firmware after RX reflash: TX and RX loaded persisted
  counter state `last=1`. One TX button press produced authenticated
  `COMMAND(TRIGGER) seq=2`; RX logged the command with RSSI `-43` and SNR `7`,
  pulsed the actuator, sent authenticated ACK `seq=2`, and TX logged the
  matching ACK with RSSI `-43` and SNR `9`.
- TEST-001, authenticated firmware after D019 build-time provisioning checks:
  TX and RX loaded persisted counter state `last=2`. One TX button press
  produced authenticated `COMMAND(TRIGGER) seq=3`; RX logged the command with
  RSSI `-41` and SNR `7`, pulsed the actuator, sent authenticated ACK `seq=3`,
  and TX logged the matching ACK with RSSI `-43` and SNR `8`.
- TEST-001, pre-authentication firmware: one TX button press produced
  `COMMAND(TRIGGER) seq=1`; RX logged the command, pulsed the actuator, sent
  ACK, and TX logged matching ACK success.
- TEST-002: the TX button was held for about 12 seconds; TX sent only one
  command, waited for button release, and returned to ready after release.
- TEST-003: a duplicate was generated by letting RX execute `seq=1`, resetting
  only TX so it restarted at `seq=1`, and pressing the TX button again. RX
  logged `duplicate ... actuator suppressed`, sent ACK again, and TX reported
  success.
- TEST-004: RX was removed from USB. TX sent the initial command plus three
  retries, logged `command final failure`, and returned to ready after button
  release.
- TEST-007: removing RX RFM95W VCC at runtime first exposed that receive
  timeout alone did not trigger recovery. RX now probes and refreshes RX mode
  after receive timeouts. Retest passed: RX detected version `0x00`, retried at
  the configured interval, detected version `0x12` after VCC returned,
  re-entered RX mode, received the next command, and sent ACK.
- TEST-008: removing TX RFM95W VCC while TX was idle and pressing the button
  produced a local send failure (`ret=-11`). TX reported the command failure,
  started radio recovery in the same button cycle, detected SX1276 version
  `0x12` during recovery, and returned to ready without requiring repeated
  failed presses. The next button press sent `seq=2`; RX triggered the actuator
  and ACK returned on the first attempt.

After authenticated monotonic counters, resetting only TX is no longer a valid
way to create a duplicate sequence: TX persists the counter and will continue
with the next sequence. Lost-ACK duplicate testing must keep the same signed
packet in flight, either by inducing ACK loss or by using a protocol test
harness.

## TEST-001 - Normal Trigger Flow

Given:

- TX and RX are powered over USB;
- both RFM95W modules are connected with antennas;
- TX button and status LEDs are wired;
- RX actuator and status LEDs are wired.

When:

- the TX button is pressed once and released.

Then:

- TX logs one debounced button press;
- TX sends one `COMMAND(TRIGGER)` with a new sequence number;
- RX logs the command;
- RX pulses the actuator LED once;
- RX sends an ACK for the same sequence;
- TX logs the matching ACK and lights the success LED;
- TX error LED remains off.

## TEST-002 - Button Held

When:

- the TX button is held down for several seconds.

Then:

- TX emits only one command for that hold;
- TX logs that it is waiting for button release;
- no second command is sent until the button is released and pressed again.

## TEST-003 - Lost ACK / Duplicate Command

When:

- the ACK for a command is lost or the TX times out while waiting for it.

Then:

- TX retransmits the same sequence;
- RX logs the repeated sequence as a duplicate;
- RX sends ACK again;
- RX does not pulse the actuator LED again for that duplicate.

Note:

- do not simulate this by resetting only TX. The authenticated firmware stores
  the TX sequence in NVS, so a reset should not reuse the previous sequence.

## TEST-004 - Receiver Unavailable

When:

- RX is powered off or out of range;
- the TX button is pressed once.

Then:

- TX attempts the initial send plus `CONFIG_GATE_TX_MAX_RETRIES` retries;
- TX logs a final failure;
- TX lights the error LED;
- TX returns to waiting for button release and then to ready state.

## TEST-005 - Invalid or Oversized Packet

Given:

- protocol host tests are run with twister.

Then:

- short, long, unknown-version, unknown-type, unknown-command, reserved-device,
  and reserved-sequence packets are rejected;
- oversized radio frames are rejected before decode.

## TEST-006 - Incorrect ACK

Given:

- protocol host tests are run with twister.

Then:

- an ACK only matches when device id, sequence, and command all match the
  command currently in progress;
- stale ACKs, unrelated ACKs, and command echoes are ignored.

## TEST-007 - Radio Failure Recovery

When:

- the radio is unavailable at boot or returns repeated runtime errors.

Then:

- firmware does not terminate the main loop;
- logs show paced recovery attempts;
- RX re-enters receive mode after recovery;
- TX can send again after recovery.

## TEST-008 - TX Idle Radio Power Loss

When:

- TX and RX are running normally;
- only the TX RFM95W loses VCC while the TX ESP32 stays powered;
- the TX button is pressed once;
- TX RFM95W VCC is restored.

Then:

- TX reports the first command as failed;
- TX starts radio recovery on that same button cycle;
- if the module remains unreadable, TX logs paced recovery attempts;
- TX logs radio recovery after the module answers again;
- the next TX button press succeeds without requiring repeated failed presses.

## TEST-009 - Packet Authentication

Given:

- protocol host tests are run with twister.

Then:

- a known HMAC-SHA256 test vector produces the expected 8-byte `auth_tag`;
- `COMMAND` and `ACK` tags differ because message type is authenticated;
- tampered packet fields are rejected;
- tampered tags are rejected;
- packets checked with the wrong key are rejected.

## TEST-010 - Authenticated Replay

Given:

- sequence host tests are run with twister.

Then:

- the first authenticated command for a transmitter executes;
- the same sequence is treated as a duplicate and remains ACKable;
- a higher sequence executes and becomes the new stored sequence;
- a lower sequence is rejected as replay;
- counter wrap from `UINT32_MAX` to `1` is rejected.

## TEST-011 - Bench Replay Rejection

Given:

- TX and RX run authenticated firmware with a provisioned shared key;
- both have persisted counter state from at least one accepted command.

When:

- the RX is reset (power cycled, not reflashed) so it reloads its stored
  sequence;
- a previously accepted command is presented again.

Then:

- RX logs `rejected replay` with the offending sequence and its stored `last`;
- the actuator does not pulse;
- no ACK is sent;
- the next genuine TX button press is still accepted and actuates normally.

This is the test that proves persistence is doing its job. Before Phase 8 a
receiver reset forgot the last sequence and re-executed the retransmission; the
whole point of the NVS counter is that it no longer does.

## TEST-012 - Bench Authentication Rejection

Given:

- TX and RX run authenticated firmware;
- the TX is reflashed with a shared key that differs from the RX key in one
  character.

When:

- the TX button is pressed once.

Then:

- RX logs `authentication failed` with `ERR_TAG` and the packet fields;
- the actuator does not pulse;
- no ACK is sent;
- TX exhausts its retries and reports final failure;
- after reflashing the TX with the correct key, the next press succeeds.

Note that this consumes TX sequence numbers, which is expected: reserving a
sequence before sending means a rejected command still burns its number.
